How to read: two bars per policy — slim translucent = static ask, full = collected. Color = the tax base the revenue lands in; left of $0 = a base it drains. Full bar shorter than the slim one = behavior leaked; longer = added. Build order runs 0 → 2, top to bottom.

Look at the capital-gains bar across the two panels. Under step-up it collects $234B of a $547B ask ($313B leaks). Stacked on taxation at death it collects $401B — the same rate increase raising $167B more, because deferral no longer lets gains escape. The direct tax on gains realized at death is now its own base (hatched), not ordinary income: it is a capital-gains tax collected at death, so booking it as ordinary would misstate the base. Ordered stacking — each bar is package − the layers below — so the bars sum to the package. Source: Tax-Simulator dials-v2 surrogate. The gains-at-death carve is applied here in post-processing (the deemed tax, folded into the income-tax head upstream, split back out); production wants it carved in the extractor alongside the preferential-rate carve.

On the two bars. The slim translucent bar is the static ask, with the same base breakout as the collected bar beneath it — so leakage and additions read as the full bar falling short of, or pushing past, the slim one, base by base, instead of a single dashed outline. The package row carries the same treatment: it is the sum of the policy rows above it, static and collected alike.
