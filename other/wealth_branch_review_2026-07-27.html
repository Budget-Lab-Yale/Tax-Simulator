Problems that can affect results or records

Fixed + tested

1. Scenarios using different Tax-Data versions can silently lose people

In everyday language A run may compare several scenarios that use different versions of the underlying household data. The simulator makes one master list of people to include, but it builds that list using only the first scenario's data. Anyone who exists only in another scenario's data is then removed from that scenario without a warning.

This is especially concerning for newly added people near the top of the wealth distribution. The code itself documents a previous case where an incomplete list removed 935 records holding $8.2 trillion in wealth and reduced expected estate tax by roughly one third. The present code fixed that problem across years within one data version, but not across different data versions.

This can happen even when the user asks for the full sample. The results can therefore look complete while actually excluding records.

Technical mechanism In parse_globals(), interface_paths is filtered to Tax-Data and then reduced with slice(1). The code reads IDs for the requested years from that one tax_data_root and stores them in globals$sample_ids. Later, run_one_year() reads each scenario's own Tax-Data file but immediately applies filter(id %in% globals$sample_ids). Thus the per-scenario input path is respected, but its population is restricted to IDs found in the first path.

Failure mode: suppose the baseline uses vintage A and a reform uses vintage B. If vintage B adds ID 9001, ID 9001 is absent from the global universe and is removed from the reform. No subsequent comparison can recover it. Because both outputs have already been restricted, later checks for matching populations may still pass.

Recommended decision If mixed Tax-Data vintages are supported, collect IDs from each distinct Tax-Data root and year before sampling, then draw one reproducible sample from the union. If comparable populations are a design requirement, reject mixed universes explicitly and report the differing paths and ID counts. Add a regression test with an ID present only in the second vintage.
Technical evidence
Primary locations: the population is taken from the first Tax-Data path in src/misc/config_parser.R, around lines 310–335. All later scenario data is restricted to that population in src/sim/run.R, around lines 792–804.
Fixed + tested

2. A valid list of years can be accepted in one place and fail in another

In everyday language The simulator says that years may be entered as one year, a continuous range, or a list with gaps. One part of the simulator understands all three forms. Another part understands only continuous ranges.

For example, a request for 2026 and 2028—but not 2027—is considered valid when the scenario is first read. Later, while choosing the household sample, that same request can fail or turn into missing values.

The underlying cause is straightforward: two separate pieces of code interpret the year entry differently.

Technical mechanism parse_year_spec() correctly recognizes a scalar year, a colon range such as 2026:2028, and a whitespace list such as 2026 2028. However, parse_globals() splits the same field only on :, converts the result to integers, and constructs x[1]:x[length(x)]. A whitespace list is therefore converted as one invalid integer rather than two years.

Failure mode: the scenario-level parser accepts the runscript, but global sample construction later emits a coercion warning, creates NA, or fails while constructing a sequence. This is a split contract: whether an input is “valid” depends on which part of initialization is reading it.

Recommended decision Replace the bespoke year parsing in parse_globals() with map(runscript$years, parse_year_spec), followed by unlist() and unique(). Add coverage for a scalar, a range, a non-contiguous list, and malformed mixtures.
Technical evidence
The full year reader is parse_year_spec() in src/misc/scenario_config.R, around line 864. A second, range-only interpretation appears in src/misc/config_parser.R, around lines 322–327.
Fix first

3. Some approved calibration exceptions are recorded as if no exception existed

In everyday language A calibration may be older than the inputs it depends on. A scenario can deliberately approve that situation by giving a dated explanation. The simulator correctly allows the run, but the final record can incorrectly say that no exception was used.

This does not necessarily change the numerical answer. It does weaken the audit trail: someone reviewing an old run may believe every calibration was current when the run actually relied on an approved exception.

The simulator supports two places for these exceptions. The safety check considers both places, while the final report considers only one.

Technical mechanism calib_check_staleness() forms the effective waiver set with modifyList(calib_waivers(...), calib_pointed_waivers(...)). By contrast, calib_manifest() calculates each waived value using only !is.null(entries[[name]]$waiver). It never consults behavior_spec$waivers, although those waivers may have been the reason the staleness check allowed the run.

Failure mode: a behavior alternative carries a durable, dated waiver for bathtub.eta_logs. The run proceeds, but the corresponding row in calibrations.csv has waived = FALSE. The numerical result is unchanged; the reproducibility record is false.

Recommended decision Factor the effective-waiver calculation into one helper used by both staleness checking and manifest creation. The manifest should ideally store the waiver source, date, and reason—not only a Boolean—so the run can be audited without reopening scenario files.
Technical evidence
The two waiver sources are combined for the safety check in src/misc/calibrations.R, around lines 245–261. The final manifest checks only the calibration file itself around lines 327–367.

4. The tests are no longer a dependable safety net

Fix first

Several tests fail before they test the behavior they were meant to protect

A test is valuable only when a failure tells us that current behavior has broken. Several tests on this branch instead fail because they still use old function names, old settings, or an old command format.

Technical assessment The newer configuration-focused tests are healthy, but the broader test directory is not aligned with the configuration refactor. This is more than cosmetic test debt: the SLURM dependency test exits at launcher argument validation, while multiple model tests stop on missing symbols or inactive configuration before reaching their numerical assertions. Those paths therefore lack meaningful regression coverage.
Area What happens now Why that matters
General source test It expects retired functions including assumption() and assumptions_load_defaults(). It stops before completing its intended checks.
Configuration stamp test It reports 23 failures because it expects values and wording from an earlier stage of the redesign. Real regressions are difficult to distinguish from deliberately changed expectations.
Cluster dependency test Its run_launcher() passes the retired user_id, producing nine arguments; slurm_run.sh rejects that form. It exits before checking whether cluster jobs depend on one another correctly.
KG and wealth tests Several refer to retired globals such as KG_DYN_CHAR_EXTENSIVE_INTERCEPT and WEALTH_CHI_PUB, or call kg_setting()/economy_param() before configuration activation. Important model behavior is not being tested through the current public interface.
Calibration writer 27 of 28 checks pass; one fails because of an extra blank line at the end of a shipped file. This is minor, but it leaves the suite red and makes future failures less noticeable.
Recommended decision Define one documented test entry point. Update active tests to construct and activate a minimal scenario through the current configuration API. Move migration snapshots to a clearly historical directory or delete them after approval. Make the entry point fail on any active test failure so a clean run has an unambiguous meaning.
Examples and locations
Examples include other/agent_workflow/test_source_all.R, other/config_redesign/check_stamp_values.R, several files in other/kg_model_tests/, and other/performance/test_slurm_dependency_graph.sh. The cluster test passes nine arguments around lines 80–83, while the launcher now rejects that old form.

Other safety and record-keeping gaps

Important

5. The scenario record does not behave as its documentation says

In everyday language The documentation says that when a scenario changes an assumption, it replaces the value and the descriptive information attached to that value. The code replaces the value but continues to use some descriptive information from the default scenario.

This creates ambiguity when reviewing a run later. The number came from the alternative scenario, but its category or explanation may still look as though it came from the default.

Technical mechanism config_resolve() reads an alternative entry's value, records the alternative as the override source, and replaces only values[[channel]][[name]]. config_manifest() later takes kind from defaults$entries. The README, however, says value, kind, and provenance are replaced together. Current files mostly contain sparse value overrides, so the implementation and the written contract disagree.
Choice to make If alternatives are intended to contain only changed numbers, update the documentation and make their source unmistakable in the run record. If they are intended to replace the entire entry, require and use the accompanying descriptive information.
Important

6. Incorrect run settings are accepted too easily

In everyday language Several settings are converted into numbers but are not checked to make sure those numbers make sense. A sample percentage can be negative or greater than 100%, yes/no choices can contain unrelated numbers, and malformed run labels are accepted until later.

These mistakes will often produce an error eventually, but the error may occur after files have been prepared and may not explain the actual mistake. In other cases, an unexpected value can quietly select the wrong behavior.

Technical mechanism The CLI layer primarily uses as.integer() and as.numeric(). It does not immediately check for NA, bounds, enumerated values, or the documented vintage format. The multicore value is validated later in parse_globals(), after some initialization. MTR variable and MTR type lists are also parsed independently, even though later map2() processing requires compatible lengths.
Recommended decision Add one early validator before output-directory or manifest creation. Require 0 < pct_sample <= 1, restrict Boolean-like flags to their accepted values, validate multicore and the vintage format, and require equal MTR list lengths. Error messages should name the bad value and the accepted form.

Simplification opportunities

Simplify

7. The cluster launches preparation jobs that do nothing

Every comparison scenario receives two KG preparation jobs, including scenarios that do not use the KG model. Those jobs start R, load the project, discover that no work applies, and exit.

Launching them only when KG behavior is present would reduce scheduler traffic and make the run plan easier to inspect. The wealth preparation work is already added conditionally, so there is a model to follow.

Current structure src/slurm/setup.R emits Phase 1B and Phase 2B task ranges for every counterfactual. slurm_run.sh submits those arrays and makes later work depend on them. For a scenario without the relevant KG configuration, src/slurm/frozen.R and src/slurm/bathtub.R load the R environment and exit without producing scenario work.

The three small preparation programs for frozen, bathtub, and wealth work also repeat nearly identical startup code. One program with a named mode could replace all three.

Suggested implementation Build task ranges from scenario capabilities: emit 1B/2B only for KG, retain the existing conditional 2N/2W wealth logic, and represent an absent range explicitly in the submission plan. Replace the three pre-pass entry files with one dispatcher taking a validated phase name. Extend the dependency-graph test to cover ordinary-only, KG, wealth, and mixed runs.
Simplify

8. Local runs and cluster runs repeat the same setup process

Important preparation steps are written separately in the ordinary runner and the cluster runner. These include preparing tax law, indexes, VAT offsets, and baseline marginal-tax information.

They currently appear broadly consistent, but every future change must be made in both places. A shared preparation function would make it much harder for local and cluster results to drift apart.

Repeated responsibilities main.R and src/slurm/setup.R both assemble the scenario context: VAT-offset decisions, indexes, tax law, and baseline MTR inputs. Bootstrap/source predicates are also repeated in main.R, src/slurm/setup.R, and src/slurm/common.R. These are control-flow decisions, so divergence would change results rather than merely style.
Suggested implementation Extract a side-effect-limited prepare_scenario_context() returning a named object consumed by both runners. Keep cluster submission outside that helper. Centralize project bootstrapping in one sourced file.
Simplify

9. Many behavior files repeat the same method with different numbers

Several KG, charitable-giving, and overtime variants contain nearly the same calculations. Most differences are a small set of assumptions.

Keeping one reviewed calculation and separate, readable assumption files would reduce the chance that a bug fix is applied to one variant but missed in another. The assumption files can remain explicit enough for researchers to audit.

Candidate families The repeated families include multiple KG numbered variants, the charitable-giving 50/100 variants, and the overtime France variants. The safe refactor is not to hide these choices in generic metaprogramming: retain named scenario modules, but have them call one shared calculation with an explicit parameter list.
Simplify

10. Some unchanging information is reread for every year

Estate-tax settings are read again while processing each year, even when all those years use the same underlying data. Reading them once for each data version would make the flow clearer and save repeated work in multi-year local runs.

Suggested implementation Cache get_estate_params() by the normalized Tax-Data root, or load it while preparing the scenario context and pass the result into run_one_year(). Prefer the latter if explicit data flow is more important than a process-level cache.
Housekeeping

11. Temporary output is mixed into a very large branch

The branch contains roughly 5,000 changed files, including about 4,000 YAML files. It also contains scheduler output, log files, LaTeX build products, a compiled Python cache file, and a ZIP archive.

Some final reports may be worth preserving, but temporary build output makes the branch harder to review and search. Ignore rules do not remove files that were already added to version control.

Observed file classes The branch diff contains 49 .out files, 9 .log files, LaTeX .aux output, a tracked .pyc cache file, and a ZIP archive. There are also many legitimate CSV, HTML, and PDF research products, which should be distinguished from disposable execution output rather than removed wholesale.
Recommended decision Keep intentional research products in a clearly named results area with a short explanation of how they were produced. Remove temporary logs, caches, and build products from version control in a later, approved cleanup.
